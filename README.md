# Alien Trilogy (PS1) matching decompilation

A reconstruction of the C source of *Alien Trilogy* (Probe Entertainment / Acclaim, 1996) for
the PlayStation, USA release (`SLUS_000.07`). The source is written so that the game's original
compiler, with its original flags, turns it back into the exact bytes of the retail executable,
function by function. The aim is readable code with real names and types; a byte match is the
proof that the reconstruction is faithful, not the end goal.

This repository contains no game data and no Sony or SN Systems software (see
[Requirements](#requirements)).

Note that this was done with an obscene amount of AI assistance. I've done my best to keep code 
quality at a readable level, but there's some stuff here that's pretty clumsy. I'm releasing this
in the hopes that I can find people interested in collaborating to improve the code readability and
help ensure naming accuracy.

About half of the executable is now compiled from reconstructed C. Almost all of the rest is
either hand-written assembly or Sony's own libraries, which are identified but not
decompiled. The remaining 17 KB is in 452 gaps; 427 of them are 4 bytes or fewer, and 17
larger gaps of up to 1.9 KB hold most of the bytes.

A byte match alone does not make a function finished. **637 of the 645 byte-matched functions
are also matched under the project's code rules** (`tools/rules.py`): no fake code, no raw
offset access, declarations in their owning headers, no placeholder steering. The other 8 are
marked `MATCH-PENDING`: their bytes are exact, but the source still relies on a construct the
rules reject, and each carries a note saying what has been tried.

`PROGRESS.md` holds the same table as generated by `tools/progress.py`, which cross-checks the
gate's record against an independent per-function comparison and fails if they disagree.

## What has been decompiled

35 C units (about 29,000 lines), grouped by subsystem:

- **Core:** `main` (boot and the main loop), `tasker` (the cooperative task system),
  `geometry`, `text`, `sprites`, `texture_upload`, `movie`
- **Gameplay:** `player`, `actor` (aliens, colonists and their AI and animation),
  `weapon_slots`, `particle`, `particle_hits`, `debris`, `effects`, `lights`, `doors`, `lift`,
  `map_objects`, `level_triggers`, `countdown_timer`, `command_sequencer`
- **Rendering:** `model_draw`, `object_render`
- **Front end:** `frontend`, `pause_menu`, `hud`, `save_password`, `memcard`
- **Audio:** `audio`, `audio_control`, `music_control`
- A few units (`game_20000_*`, `game_helpers7`) still hold functions whose subsystem is not
  settled yet.

Unit file names describe what the code does. They are not evidence of the original file
layout. Shared types live in `include/`, one owning header per subsystem (`ACTOR.H`,
`LEVEL.H`, `TASK.H`, ...).

The code follows id Software's Quake III C style: `Prefix_VerbNoun` functions with a module
prefix (`Actor_PlayAnimation`, `Door_Init`), `lowerCamel_t` types, `lowerCamel` members, `g_`
globals, K&R layout with spaces inside parentheses (`.clang-format`), and a box banner above
each function. Names that come from evidence outside this game keep their original spelling:
Sony library names, and names from lineage source. Probe's later *Forsaken* (PC) shares
framework code with this game, and its `Tasker.c` is the direct descendant of `src/tasker.c`
(`TaskerInit`, `TASK`).

Names are semantic wherever there is evidence for them; 7 functions are still named after
their address (`f_xxxxx`), each with a note saying what was checked. Comments in the source
mark where each name comes from (`name: inferred from ...`, `names invented`).

The renderer at `0x80048f54`–`0x800588bb` is hand-written MIPS/GTE assembly in the original.
It lives in `asm/` as heavily annotated `.s` files assembled by ASPSX, and is counted
separately from C.

## Layout

| Path | Contents |
|---|---|
| `src/` | Reconstructed C units. Every function here is a full byte match. |
| `include/` | Shared types and declarations, one owner per type or symbol (`include/README.TXT`). |
| `asm/` | The 11 hand-written renderer units. |
| `asm/lib/` | 29 Sony library modules that match no archived SDK version, as annotated assembly (`docs/notes/library_asm.md`). |
| `config/` | Per-unit symbol maps (function and data addresses and sizes, every referenced symbol), `data.json` (initialized data placement), BSS and section layout, the gate's hash contract, the toolchain lock. |
| `tools/` | Build, verify, gate, diff and report tools (Python, standard library only except `diff.py`). |
| `analysis/` | Sony library identification (`runtime_*.py`), the link plan, startup and GP layout, symbol inventory, validation scripts. |
| `reports/` | Generated results: `latest.json` (per-function verification), `progress.json`, `link_plan.json` (the remaining gaps). |
| `docs/notes/` | Notes on the toolchain, GCC 2.5.7 codegen, the task system, the heap and the linker. |
| `AGENTS.md` | Working rules for contributors, human or automated. |

## How verification works

- **`tools/build.py`** compiles one unit with the original DOS toolchain under DOSBox-X.
- **`tools/verify.py`** builds every unit and compares each function and data item with the
  retail bytes. The comparison includes the target of every relocation, so a function that calls
  the wrong function or names the wrong global does not count as matched.
- **`tools/gate.py`** is the final check:
  1. It rebuilds everything into a fresh directory.
  2. Its own linker applies every relocation and places the matched code and data over the
     original executable.
  3. It requires the whole PS-X EXE to hash to the retail SHA-256.
  4. It writes a per-byte provenance record and checks it against `verify.py`.

  The only success output is a single `GATE OK` line. On failure it names the unit and function
  behind every differing byte.

Only code that passes all of this is in `src/`. Partial reconstructions are kept out of the
build.

## Requirements

You need to supply:

- your own copy of the retail executable, at
  `../games/Alien Trilogy (PS1 USA)/extracted/SLUS_000.07`;
- the PsyQ toolchain under `../toolchain/`, with the exact files whose hashes are pinned in
  `config/toolchain.lock.json` (GCC 2.5.7 `C257`, the ASPSX assemblers, and
  `binutils-mips-decompals` v0.10);
- the Runtime Library 3.3 SDK under `../sdk/`, and `../shared-tools/psyqobj.py`;
- Python 3 and [DOSBox-X](https://dosbox-x.com/) at `C:\DOSBox-X\dosbox-x.exe`;
- `capstone` (`pip install -r requirements.txt`), needed only by `tools/diff.py`.

Paths are relative to this checkout, so it must sit next to those directories.

## Usage

```
python tools/gate.py                       # whole-executable byte gate (about 2 minutes)
python tools/verify.py                     # per-function verification, writes reports/latest.json
python tools/verify.py --units player --output builds/player.json   # one unit
python tools/build.py --source src/player.c                         # compile one unit
python tools/diff.py --object builds/job-*/INPUT.OBJ --symbol-map config/player.json --function <name>
python tools/rules.py --report-only        # code-rule check: matched under the rules, MATCH-PENDING
python tools/reports.py --jobs 6           # gate, verify, library reports, rules, link plan, PROGRESS.md
```

Run the gate from a clean tree; it refuses to bank anything else. Tool tests use
`python -m unittest tools/test_<tool>.py`. `tools/test_elf_lnk.py` needs two ELF fixtures
that are not published.

## Open issues

- **Remaining gaps:** the 452 gaps listed in `reports/link_plan.json`.
- **MATCH-PENDING functions:** 8 byte-exact functions whose honest spelling is still unknown,
  listed in `config/match_pending.json` with what was tried (`Menu_CreditsLineTask`,
  `Menu_MessageBoxType`, `Card_WriteFile`, `Particle_DrawDebris`, `Object_PickupsTask`,
  `Door_Blocked`, `Door_PrepareModels`, `Lift_PrepareModels`).
- **`_spu_RXX`:** Sony's `S_GKS` and `S_SCA` modules imply two different addresses for it, so
  both are rebuilt as library assembly instead of being certified as Runtime 3.3.
- **Layout:** the gate places matched code and data at the addresses in the symbol maps. A link
  from source alone, without the original as fallback, is not attempted yet.
- **Names and types:** a byte match proves the generated code, not the names or types. Some
  names and struct layouts are still provisional.

## Contributing

Read `AGENTS.md` first. In short:

- only full matches enter `src/`;
- no inline assembly outside the permitted renderer and library ranges;
- no magic numbers;
- no fake code or padding to move a score;
- Quake III naming and layout (`config/style_renames.json`, `.clang-format`);
- nothing is "matched" until the gate prints `GATE OK`, and a function counts as finished only
  when `tools/rules.py` also passes it.
